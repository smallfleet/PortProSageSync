PortProSage Sync — Technical Design Document

The engineering-level reference: the environment it requires, the exact PortPro and Sage 50 APIs it calls, the business logic that decides what happens to every invoice and customer, and the process/data flow end to end.

This assumes you already know what the app does for an operator — see USER_GUIDE.html for that. This document is for whoever maintains, extends, redeploys, or troubleshoots the system at the code level. Quick-start build/run instructions live in README.md.

1. System overview

PortProSage Sync moves invoice and customer data one way: PortPro (source of truth) → Sage 50 Canadian Edition (destination). It runs as a Windows Service that either polls PortPro on a schedule or executes a single explicit request, validates/maps each invoice against Sage 50's own master data (customers, items, GL accounts), and posts it via the Sage 50 SDK. A separate WinForms Admin application edits configuration and starts/stops/monitors runs — it never talks to PortPro or Sage 50 itself.

Nothing is ever pulled back out of Sage 50 into PortPro. The one exception that touches Sage 50 without an invoice attached is the customer-profile push (incremental sync or the Customer Refresh tab) — still one-directional, PortPro → Sage 50.

Why file-drop instead of a network/IPC API

The Admin app and the Service communicate purely through the filesystem: a SyncRequest is serialized to <id>.request.json, the Service processes it and writes <id>.result.json next to it, checkpointing after every invoice so a killed process still leaves a real partial result behind. Chosen over a REST endpoint or named pipe because the trigger tool needs zero network/IPC setup (just filesystem access, works from a scheduled task or mapped drive unchanged); a result file surviving on disk after its writer exits is exactly what History & Logs is built to read; and it naturally serializes access — only one process can plausibly be mid-write to Sage 50 at a time in practice.

4. PortPro API surface

Every endpoint, base URL, and query parameter name below was confirmed live — either by extracting string literals from the previously-working connector tool's compiled binary and testing them against the real API, or by direct curl calls against production using the real refresh token. Where a name looks like it doesn't quite match its semantic meaning (billingFrom/billingTo used for the "invoice date" filter), that's the confirmed real parameter name, not a guess.

4.1 Authentication

  • PortPro issues an Access Token + Refresh Token pair directly (no client id/secret, no standard OAuth flow) — configured once as PortPro:AccessToken/RefreshToken (secrets, kept out of appsettings.json).
  • POST {BaseUrl}/generate-new-token mints a fresh access token from the refresh token — called automatically when the cached token is judged expired, and on-demand on a 401 (retrying that one request exactly once with the new token).
  • Every request carries Authorization: Bearer {accessToken}.
  • 429 Too Many Requests is retried with backoff (honoring Retry-After when present, exponential up to 30s otherwise, up to 5 attempts) — added after a large InvoiceNumberList run's rapid single-invoice lookups triggered rate limiting that, unhandled, failed the entire run instead of just one lookup.

4.2 Invoices — list endpoint

GET {BaseUrl}/invoices, paginated via skip/limit (limit = PortPro:PageSize, default 100). Every page of every list call also sends allInvoices=true.

Sync modeQuery parameters addedNotes
LastChangedDateupdatedFrom/updatedToPortPro's "last touched" timestamp — can include an invoice dated well outside the window if merely edited.
CompletedDateRange ("Invoice date")billingFrom/billingToThe invoice's own real date, despite the parameter name.
InvoiceNumberRangebillingFrom/billingTo widened to 10y back → tomorrowNo server-side reference-number filter exists. An unbounded query was confirmed to make PortPro silently omit real invoices (multi-charge-set ones); a date-bounded query returns the complete set. Filtered by ReferenceNumber client-side.
InvoiceNumberList / GapScann/aUses the single-invoice endpoint instead — see 4.3.

Response shape: {"data": [{load fields..., "invoice": [charge-set fields...]}]} — one data entry is one PortPro load; its invoice[] can hold more than one charge set. Flattened so nothing downstream deals with the envelope.

An unrecognized FilterType reaching the query builder throws immediately rather than silently sending no filter — a deliberate guard after a version-skew incident where an older Service build, given a request from a newer Admin build using an unknown FilterType, fell through with no filter and began really importing the entire production account. See §13.

4.3 Invoices — single-invoice endpoint

GET {BaseUrl}/invoices/{referenceNumber} — looks up one invoice directly, bypassing pagination. Confirmed to find at least one real invoice the list endpoint could not return under any query tried. Used for InvoiceNumberList (one-at-a-time, 150ms pace between calls; a 404 is logged and skipped, not fatal), InvoiceNumberGapScan (rewrites into InvoiceNumberList internally), and the --check-invoice diagnostic. Wraps its response differently than the list endpoint, and one reference number can legitimately span multiple charge sets that get combined (amounts summed, pricing lines concatenated), not treated as duplicates.

4.4 Customers

Confirmed live to be a separate, richer object from the lightweight caller embedded on each invoice (_id, company_name, currency, externalSystemID only):

  • GET {BaseUrl}/customer/{id} — one customer's full profile, ~94 fields. id = invoice.caller._id.
  • GET {BaseUrl}/customer, paginated — the entire list, same full-profile shape as the single fetch, so a full scan (~223 customers on this account) needs no per-customer detail call.

Confirmed live 2026-08-23: this endpoint silently caps every response at 50 records, ignoring the requested limit — direct calls with limit=100 each returned exactly 50 at skip=0/50/100; /invoices correctly honors limit=100. GetAllCustomersAsync's original pagination-termination check silently truncated a full-account scan to the first 50 customers. Fixed by advancing skip by the actually-returned count and stopping only on a genuinely empty page. See §13.

4.5 Per-invoice payment terms

Confirmed present on the invoice envelope (sibling to _id/invoice/createdAt), not the customer object — genuinely varies per invoice: payment_terms (→ PaymentTermsNetDays), payment_terms_method, invoiceDueDate (present but not currently consumed — Sage 50's own due-date calculation from the days value is used instead, so it stays consistent with Sage 50's own invoice date).

4.6 Known API-shape gotchas

  • Pagination instability against a live dataset. A gap-fill sweep re-fetching the exact same range a prior run just fetched can occasionally still find "missing" invoices — confirmed this is records shifting between sequential skip/limit calls against live, mutating data, not a systemic omission. This is why gap-fill is a permanent safety net (§6.9), not a one-time fix.
  • Multi-charge-set invoices can be invisible to the list endpoint. A confirmed real case (2 charge sets, same reference number) never appeared via the list endpoint under any query, while a single-charge-set neighbor did. The single-invoice endpoint found it fine.

5. Sage 50 SDK surface

This is a managed .NET assembly (SimplySDK namespace, ships as Sage_SA.SDK.dll), not a COM component — there is no ProgID to resolve; it's referenced and called directly, confirmed against the SDK's own shipped XML documentation and cross-checked with live reflection over the shipped assembly plus live calls against a real company file.

5.1 Connection model

Sage50Client is a DI singleton with a connected flag — ConnectAsync is idempotent after the first real connect. The three long-lived ledgers are opened once and reused, not reopened per call — confirmed live that opening/closing has real overhead, and a 120-invoice run was doing this several times per invoice. SalesJournal is deliberately not pooled the same way — opened fresh and closed per invoice, since a failed write has real incident history (§13) of leaving a session in a bad state.

5.3 Confirmed limitations (verified via live reflection, not assumed)

  • No per-customer receivable/AR account property exists at all. Sage 50 posts every customer to one global AR control account, configured once in Sage 50 itself — not settable per customer regardless of Sage50:DefaultReceivableAccount's value (kept for audit/logging only).
  • No per-customer payment-terms property exists either. Terms live only on the invoice-posting object — must be set explicitly on every single invoice (§6.8).
  • SelectAPARLedger does not auto-populate payment terms.
  • Re-reading InvoiceNumber after Post() is unreliable — the code returns the value it set before posting, not what it reads back afterward.
  • Any unhandled exception from a real write is treated as evidence of a possibly-compromised SDK session and terminates the whole process — see §10.

6.2 Watermark / "Continue"

A persisted (date, last-processed-invoice-number) pair in state.db. A UseWatermark=true request resolves From from the saved date and To as "now"; only a watermark-driven run advances it afterward. Every other mode is a one-time override that never reads or writes it — proven by capturing Before/After on every run, showing an explicit-range run leaves it genuinely untouched.

6.3 Cutoff (lower) invoice date

Sync:CutoffInvoiceDate — a hard floor applied identically regardless of mode: an invoice dated before this is skipped outright, never attempted against Sage 50. Stops Sage 50's own "Do Not Allow Transactions Dated Before…" configuration from rejecting an invoice mid-run.

6.4 Max invoices / max customers cap

Enforced inside the same run's own loop, not by pre-computing a boundary for a separately-refetched run (confirmed that approach doesn't reliably cap anything against live data). Counts only genuinely processed items — imported + failed validation + failed write for invoices. MaxInvoicesToProcess has no equivalent on the Customer Refresh tab's Run Selected (§6.10) — its scope is exactly the rows the operator ticked, not a numeric cap.

6.5 Dry Run — two independent flags

FlagConfig keyScope
Shared Dry RunSage50:DryRun (persisted)Every ordinary Manual Run, the Automatic Service, and the periodic customer-sync sweep. Editable identically on Manual Run and Sage 50 tabs — same setting, saved immediately either place.
Customer Refresh's own Dry RunSyncRequest.CustomerRefreshDryRun — never persisted, defaults to falseApplies only to that one Run Selected execution. Overrides Sage50Settings.DryRun in-memory, for that one dedicated process only (same technique the diagnostic commands use) — never touches appsettings.Local.json.

When either flag is set, every Sage 50 write call short-circuits to a log line and a synthetic DRYRUN- result without calling the SDK. MarkImported/MarkCustomerSynced/RecordCustomerRefreshOutcome are all guarded so a Dry Run result is never recorded as if real — otherwise turning Dry Run off later would make those items look "already done" forever. Confirmed 2026-08-24: CustomerRefreshDryRun now defaults to false on every request (the Admin UI's own checkbox also defaults unchecked, reversing the old "defaults to checked" behavior) — a real write is the default action for Run Selected, not a simulation.

6.6 Customer resolution, auto-create, and per-run caching

InvoiceValidationService.ValidateCustomerAsync, once per invoice:

  1. Match key is caller.company_name (falling back to callerName) — matched against Sage 50 by name only; there's no separate customer-code concept in this SDK.
  2. Per-run cache first. A customer already found-or-created earlier in this same run is never re-checked. This class is a DI singleton reused across every poll cycle, so the cache is explicitly cleared at the top of every RunAsync call, not just at process startup.
  3. Cache miss → FindCustomerByNameAsync. Found → cached and used.
  4. Not found → if auto-create is off, validation fails. If on: fetch PortPro's full profile via GET /customer/{id} when available (falling back to name + currency only if the id is missing or the fetch fails — never blocks creation), build a profile (shared mapping with the customer-sync path), create it, cache it, and record it in customer_sync_state.

Mid-run deletion recovery. Because the cache can span hours, a cached customer can genuinely be deleted/renamed in Sage 50 during the run. SelectAPARLedger independently re-validates immediately before posting — if it no longer resolves, it throws CustomerNotFoundException (recoverable — nothing was written; it's a pure selection call). ProcessOneInvoiceAsync evicts the stale cache entry and fails just that one invoice; a later invoice for the same customer in the same run gets a fresh look and a real chance to auto-recreate the customer and succeed immediately. The one affected invoice is picked up by gap-fill or the next run.

6.7 Item/GL account resolution

Each PortPro charge line is matched to a Sage 50 service item by code/description; missing ones are auto-created using a configured ChargeAccountMap entry's account, or the default revenue account as fallback. Resolution order: charge-specific mapping → default revenue account → hard error (the invoice fails rather than posting to an undefined account). PortPro's own glCode is reference/audit only, never used to resolve the posting account. Whichever account is chosen is confirmed to exist (LoadByAccountNumber, not LoadByAccountDisplayString) before import. A small allow-list (AccountsUnverifiableBySdk) bypasses the SDK check for accounts confirmed real but which the SDK itself can't verify.

6.8 Due date / payment terms

Every invoice used to post with an implicit Net 0 (SetTermDiscNetDay was never called at all), so Sage 50 always showed Due Date = Invoice Date. ResolveNetTermDays now resolves days-until-due from PortPro's own per-invoice terms (§4.5, confirmed genuinely per-invoice) when present and in units of days, falling back to Sage50:DefaultNetTermDays (default 30) with a warning otherwise. The resolved due date is recorded on the outcome and surfaced in the "Invoice Transferred" grid.

6.9 Gap-fill ("Finding the Gap")

Not a mode an operator picks — an automatic follow-up, triggered after every completed, range-based run regardless of source. Computes the lowest/highest reference number the original run actually touched, and re-runs exactly that range through the InvoiceNumberList path — checking each candidate individually, confirmed more reliable than the list endpoint for multi-charge-set invoices. Recorded as its own History & Logs entry. Skipped if the original run didn't complete cleanly, fetched nothing, or is itself a gap-fill sub-run. Remains necessary permanently — the residual symptom is pagination instability against a live dataset (§4.6), not a fixable client-side omission.

6.10 Customer sync — incremental sweep vs. Customer Refresh tab

CustomerSyncService exposes three separate public entry points (no longer one shared forceAll/maxCustomers-parameterized method):

  • SyncChangedCustomersAsync — once per Automatic Service cycle and once per Manual Run. Gated by Sage50:SyncCustomerUpdatesFromPortPro (default on). Compares each customer's updatedAt against customer_sync_state; unchanged ones skip before any Sage 50 lookup. A changed, existing customer gets updated; one not found in Sage 50 is just marked synced anyway. Never creates.
  • ScanForRefreshAsync (Customer Refresh tab's "Extract All Customer") — a read-only comparison, not a write. Fetches every PortPro customer (now genuinely the full account since the pagination-cap fix, §4.4) and classifies each INSERT/UPDATE by name match, unconditionally, bypassing the changed-since-last-sync check entirely. Also stamps each candidate's LastOperationSuccess/LastAppliedAtUtc from the persisted customer_refresh_status table (§8), so the grid can pre-fill Applied/Date from a previous session without re-running anything.
  • ExecuteSelectedRefreshAsync (Run Selected) — the actual write step, scoped to exactly the PortPro customer IDs the operator checked (CustomerRefreshSelectedPortProIds), not the whole account — a deliberate change from the old design. No max-customers cap; the selected-IDs list is the scope. A local RecordOutcome closure appends every result to the run's Outcomes (so the Admin grid updates rows in place instead of clearing) and — guarded by if (!_settings.DryRun) — persists to customer_refresh_status.

Both SyncChangedCustomersAsync and ExecuteSelectedRefreshAsync update customer_sync_state on a successful non-Dry-Run write — a real Run Selected also resets the incremental sweep's "last synced" watermark for every customer it touches.

6.11 History & Logs / audit trail

Every run produces a request/result JSON pair on disk, checkpointed live. Reconstructed into the grid from four sources (processed archive, live trigger folder, Manual Run subfolder, auto-poll subfolder) plus a log-line fallback for older entries. Deleting a run removes its files, any failed-transaction CSV, and its imported_invoice rows scoped to that run's own Sage50Path (§6.12 — grouped per distinct path across a multi-run batch delete, since a reference number is only unique within one path now), and records the deletion permanently in an exclusion list so it can't silently reappear via the log-reconstruction fallback.

6.12 Per-Sage50-path scoping

Problem confirmed live 2026-08-10 and again 2026-08-23: before this feature, every table in state.db was a single flat, unscoped bucket — switching Sage50:CompanyDataPath between two different .SAI files (e.g. DEV vs the real PROD one) meant an invoice tracked as "already imported" while pointed at one file was silently treated as already-imported when later pointed at a completely different one, even though the second file never actually received it. The same cross-contamination applied to the watermark, customer_sync_state, and customer_refresh_status.

Fix: every state-carrying table now includes a sage50_path TEXT NOT NULL COLLATE NOCASE column as part of a composite primary key, and every read/write in SyncStateRepository is scoped by a CurrentSage50Path property (Sage50Settings.CompanyDataPath, injected via DI). COLLATE NOCASE avoids needing to manually normalize path casing (Windows paths are case-insensitive) while keeping the displayed value's original casing intact for the path-picker dropdowns.

Schema migration (SyncStateRepository.Initialize): SQLite can't ALTER TABLE a primary key, so each table is migrated via PRAGMA table_info (detects whether sage50_path is already present) → rename the existing table → create it fresh with the new schema → copy every row across, backfilling sage50_path with whichever path is currently configured at the moment the migration runs → drop the renamed-aside old table, all inside one transaction.

This is a one-time, best-effort backfill, not a true historical reconstruction — a table that predates this feature has no record of which path was actually active when each row was written, so every pre-existing row is stamped with "whatever's configured right now." Confirmed as a real, non-hypothetical gap 2026-08-23: cross-referencing imported_invoice's imported_at_utc timestamps against the Service's own historical logs/*.log startup lines showed all 3,664 pre-existing rows were genuinely created while pointed at one path, while the migration (which ran later, after the configured path had since changed) had backfilled them to a different one — corrected by hand via a one-off, precisely-timestamp-matched update once identified, not by any code path.

Admin UI behavior (Customer Refresh and History & Logs, mirrored identically): the path dropdown always includes the currently-configured path but never overrides an operator's existing selection. Refreshed on both full config reload and every tab click. Selecting the current path keeps Customer Refresh fully live; selecting any other path switches it to a read-only view of that path's persisted customer_refresh_status rows. History & Logs' path filter is purely a display filter — an entry with no recorded path (pre-dates this feature, or was written by a stale Service binary — §13 item 13) always shows regardless of the selected filter, so older history is never silently hidden.

Backed on the Admin side by a parallel, Admin-only Sage50PathStateService that reads state.db directly (Admin can't reference Core — same net48/SDK dependency constraint as §3).

7. Process flows

7.1 Manual Run / Customer Refresh — end to end

  1. Operator: fills the form, clicks Manual Run / Extract All Customer / Run Selected.
  2. Admin: validates inputs, shows confirmation dialog(s) — write mode, company file, and for Customer Refresh's Run Selected, the "*** DRY RUN ***"/"*** REAL WRITE ***"-led "ALERT..!!" dialog.
  3. Admin: writes <id>.request.json, launches PortProSage.Service.exe --run-once <path>, begins polling for the result file every 2 seconds.
  4. Service: reads the request file.
  5. Service (Customer Refresh Extract — CustomerRefreshScan): fetches every PortPro customer, classifies each INSERT/UPDATE against Sage 50 by name, read-only — nothing written.
  6. Service (Customer Refresh Run Selected — FullCustomerRefresh): overrides DryRun in-memory from the request, and for each selected PortPro customer id, loads it by name in Sage 50 and saves the created/refreshed profile, or logs a DRY RUN line; records each outcome (persisted to customer_refresh_status unless Dry Run).
  7. Service (invoice sync): fetches invoices (list or single-invoice endpoint), and for each: cutoff check, already-imported check, validate customer/items/accounts, create the invoice (or log DRY RUN), checkpoint the result file.
  8. Service (invoice sync only): runs the automatic gap-fill sweep (its own History & Logs entry) and the incremental customer-sync sweep.
  9. Service: writes the final result file (IsFinal=true, including Sage50Path) and exits.
  10. Admin: detects IsFinal, stops polling, shows the completion pop-up (customer-worded "ALERT..!!" pop-up for Customer Refresh), refreshes History & Logs, updates Customer Refresh grid rows in place (Extract/Run Selected) rather than clearing them, resets one-time form fields to their defaults.

8. Local data model (state.db)

A single SQLite file (Sync:StateDatabasePath), created/migrated automatically on first use. Every table is scoped by sage50_path (§6.12) — one shared file holds every Sage 50 company file's tracking, distinguished by this column as part of each table's primary key.

CREATE TABLE watermark (
    key         TEXT NOT NULL,   -- 'last_changed_date' / 'last_processed_invoice_number'
    sage50_path TEXT NOT NULL COLLATE NOCASE,
    value       TEXT NOT NULL,
    PRIMARY KEY (key, sage50_path)
);

CREATE TABLE imported_invoice (
    portpro_invoice_id    TEXT NOT NULL,   -- PortPro's own invoice id - the real dedup key
    sage50_path            TEXT NOT NULL COLLATE NOCASE,
    reference_number      TEXT NOT NULL,   -- human-readable, e.g. RSRE_000284
    sage50_invoice_number  TEXT NOT NULL,
    imported_at_utc       TEXT NOT NULL,
    PRIMARY KEY (portpro_invoice_id, sage50_path)
);

CREATE TABLE customer_sync_state (
    portpro_customer_id TEXT NOT NULL,
    sage50_path          TEXT NOT NULL COLLATE NOCASE,
    company_name        TEXT NOT NULL,
    portpro_updated_at  TEXT NOT NULL,       -- the PortPro updatedAt this customer was last synced AS OF
    synced_at_utc         TEXT NOT NULL,
    PRIMARY KEY (portpro_customer_id, sage50_path)
);

-- New table (2026-08-24) - the persisted "last real Run Selected outcome" per
-- customer, powering Customer Refresh's Applied/Date grid columns across app
-- restarts and re-Extracts. Never written for a Dry Run outcome - see §6.5/6.10.
CREATE TABLE customer_refresh_status (
    portpro_customer_id TEXT NOT NULL,
    sage50_path          TEXT NOT NULL COLLATE NOCASE,
    company_name        TEXT NOT NULL,
    operation             TEXT NOT NULL,     -- 'INSERT' / 'UPDATE'
    success                INTEGER NOT NULL,
    message                TEXT NOT NULL,
    applied_at_utc         TEXT NOT NULL,
    PRIMARY KEY (portpro_customer_id, sage50_path)
);
  • Dedup key is PortPro's invoice id (plus sage50_path), not the reference number — the "already imported" check is keyed on the id (scoped to the current path), so a reference-number reuse can never falsely suppress a genuinely different invoice, and the same reference number legitimately existing under two different paths is not a collision.
  • imported_invoice rows are written immediately per invoice, not batched — this is what lets a killed process resume cleanly: everything already recorded stays recorded, and the watermark (which only advances once, at the very end of the loop) simply never advances for a run that died mid-way.
  • customer_refresh_status is always overwritten (not appended) on a later real Run Selected for the same customer + path — it tracks the single most recent outcome, not a full history.
  • A separate deleted-history-ids.json file (not a DB table — lives in the trigger folder) is a permanent exclusion list, so a deleted run's history entry can't reappear via log reconstruction.

10. Failure handling philosophy

Two distinct failure classes, deliberately treated differently:

Fatal — terminates the whole process. Any unhandled exception from a real (non-Dry-Run) Sage 50 write call, except the two recoverable cases below, is treated as possible evidence of a compromised SDK session and calls Environment.Exit(1) immediately. Traces back to a real incident: a genuine write failure left the SDK session itself in a bad state, and every subsequent call in that session started throwing too — but the code at the time kept catching each failure per-invoice and continuing, cascading through ~30 more invoices against an already-compromised session with no reliable way to tell which "succeeded" for real. This also gives correct watermark behavior for free — dying mid-loop means the watermark (which only advances once, at the end) is simply never reached, and invoices already durably recorded are never reprocessed on restart.

Recoverable — fails just one invoice, run continues. DuplicateInvoiceNumberException (Sage 50's own duplicate-number validation rejected the post before writing anything — evidence of correct validation, not a compromised session; the invoice is marked imported and the run continues). CustomerNotFoundException (SelectAPARLedger — a pure selection call, not a write — couldn't resolve a cached customer; the stale cache entry is evicted and the run continues).

An unrecognized FilterType reaching PortProClient.BuildQueryString also fails loudly and immediately (§4.2) rather than silently fetching with no filter — a deliberate guard against version skew between the Admin app and the Service executable processing its request.

11. Versioning & deployment

  • Version scheme: X.YY.ZZ — X major (big feature release), YY minor (a release-worthy batch, e.g. what ships in the next production installer), ZZ build (any other new exe, including small dev-test iterations). Bumped by hand with every Admin build handed out for testing.
  • Build configs: PortProSage.Service and PortProSage.Trigger built in both Debug and Release; PortProSage.Admin has a single build.
  • Deployment scripts: Install-Production.ps1 (fresh install — folders, appsettings.Local.json, Windows Service registration) and Build-Installer.ps1 (packages a redistributable installer, bundling the documentation alongside the binaries).

12. Security & secrets

  • appsettings.json is checked into source control and never contains real secrets — PortPro AccessToken/RefreshToken and Sage50 Password are always blank there.
  • appsettings.Local.json (git-ignored, copied from the .example file) holds the real values for one specific install, loaded last so it overrides the checked-in file. Each deployment gets its own.
  • The Sage 50 account used by this service is a dedicated, non-interactive account, deliberately separate from any human's own login — both for the technical reason (a second simultaneous session is rejected) and so Sage 50's own audit trail clearly distinguishes automated writes from human ones.
  • PortPro's Access Token refreshes itself automatically from the Refresh Token; neither is ever logged.

13. Confirmed quirks & prior incidents

A consolidated list of things that were tested and confirmed live, not assumed — kept here so a future change doesn't accidentally re-introduce a previously-fixed problem.

  1. PortPro's list endpoint can silently omit real invoices (multi-charge-set ones) under any query tried, while the single-invoice endpoint finds them. → Gap-fill exists permanently because of this.
  2. An unbounded InvoiceNumberRange query omits data PortPro's API otherwise has — a wide date bound was required for the complete result set.
  3. SetReferenceNumber is the wrong field for the invoice number — it's the prepayment/deposit reference and throws for a plain invoice. InvoiceNumber is correct.
  4. SelectTransType must be called before any other invoice-specific setter, or the journal defaults to a mode where they throw.
  5. A real Sage 50 write failure can leave the SDK session itself corrupted for the rest of that process's lifetime. → the fatal-write-terminates-the-process policy.
  6. LoadByAccountDisplayString does not work for existence checks — confirmed false for every real account tried; LoadByAccountNumber (numeric) does.
  7. Reading InvoiceNumber back after Post() returns an unreliable value — use what was set before posting.
  8. SetTermDiscNetDay was never called at all before the due-date fix — every invoice posted with an implicit Net 0.
  9. A version-skew mismatch between the Admin app and the Service exe can silently mean "process everything" if an unrecognized FilterType falls through to no filter — confirmed to have actually happened once. → the fail-loud guard.
  10. Rapid sequential single-invoice PortPro lookups can trigger 429 rate limiting on a large list/gap-fill run. → retry-with-backoff plus a deliberate pace between calls.
  11. Concurrent writes to the same result.json (a run checkpointing while the Admin app polls it) can hit a file-sharing conflict on a long, busy run. → retry-with-backoff on the writer, FileShare.ReadWrite on every reader.
  12. PortPro's /customer list endpoint silently caps every response at 50 records, ignoring the requested limit — confirmed live via direct calls with limit=100 each returning exactly 50 at skip=0/50/100; /invoices correctly honors limit=100. → §4.4; GetAllCustomersAsync now advances skip by the actual returned count and stops only on a genuinely empty page.
  13. A stale Service binary silently omits a newly-added SyncResult field from its written result.json (not written as null — genuinely absent) if the Core DLL it's linked against predates that field. Confirmed live 2026-08-24: the actively-running Service.exe hadn't been rebuilt after SyncResult.Sage50Path was added, so every result it wrote that day lacked the field, which (by the deliberate "unknown path always shows" rule, §6.12) made those History & Logs rows appear under every path filter instead of just the one they actually ran against. Distinct from item 9 above (that guard catches an unrecognized FilterType; this is a missing field on an otherwise-valid result) — there is no code-level guard against it. → Service/Trigger must be rebuilt (and restarted, if running as a live process) after any Core model change.
  14. Switching Sage50:CompanyDataPath without per-path state scoping cross-contaminated tracking between company files — an invoice/customer/watermark state recorded while pointed at one .SAI file was silently treated as applying to a completely different one after switching. → Fixed by scoping every state.db table by sage50_path (§6.12); the one-time migration that backfills pre-existing rows to "whatever's currently configured" is itself a known, documented limitation of that fix, not a complete historical reconstruction.
